# 跨功能共用逻辑工作清单

状态：三个阶段已完成，本地脚本已重新构建。模拟 API 和 DOM 的完整回归通过 29 项检查。

## 实施结果

1. 影视和字幕共用 `panel.js` 的 `createPanelTask`。它负责任务互斥，以及正常结束、取消或异常后的解锁。各面板管理自己的进度和停止检查。字幕回收标记为结果待确认时，须重新检查目录才能再次选择该字幕。
2. 清单导出和影视、字幕选区共用 `core.js` 的 `walkTree`。它按原顺序深度优先遍历，对重复 ID 去重，并在进入下一节点前检查停止。清单仍构造路径和校验文件元数据，媒体仍记录父目录信息和关联同目录字幕。测试覆盖 160 层目录、循环引用、读取失败及请求返回后停止。
3. `cachedDriveChildren` 共用于媒体选区、影视目标预览和 123 清单导入。缓存属于单次任务。123 导入继续在同名冲突及秒传核验时清空对应目录缓存后重新读取。

## 当前完整流程

1. `bootstrap.js` 按网盘选择入口，并在需要时提前观察页面请求，以读取当前登录状态和选区。
2. `manifest.js`、`media.js`、`subtitles.js` 分别创建网盘来源和当前任务上下文。
3. 功能读取选区与目录树：清单整理文件路径和元数据；影视、字幕筛视频、字幕及其关联关系。
4. 影视和字幕解析作品、年份、季集及候选；清单则校验文件清单和目标路径。
5. 有副作用的操作先生成或确认计划，再重新读取网盘状态核对；执行后读取结果确认或保留“结果不明”状态。
6. 可复用的数据写入缓存或账本，供下次检查、恢复和对账。

## 已经共用

- `core.js` 提供请求、请求节流、有限并发、输入与文件元数据校验、路径校验和标题规范化；`manifest.js` 与 `guangya.js` 共用分页读取。先复用现有入口，不要再造一套通用工具。
- `works.js` 已统一影视整理和字幕工作中的作品名称别名、TMDB 身份及持久作品库。它是有效的领域共享边界。
- `media.js` 的 `mediaContext` 为影视和字幕统一构造当前会话与网盘 `source`；123 使用 `pan123Source`，光鸭使用 `guangyaSource`。两种功能也共用 `collectMediaSelection` 做选区展开、视频筛选和严格的同目录字幕关联。
- 字幕批量删除调用 `media.js` 的 `recycleMedia`；123 和光鸭分别复用各自网盘已有的回收站逻辑。
- `panel.js` 已提供共用面板、功能互斥、窗口外观和面板级设置入口。功能流程和领域状态仍分别由两个功能面板管理。

## 候选清单

### 1. 收敛任务状态控制

- 依据：互斥基础在 `panel.js`；影视锁定、停止和控件更新在 `media-panel.js:83`；字幕锁定和控件更新在 `subtitles-panel.js:172`。批量遍历已经使用 `core.js` 的 `forEachConcurrent`。
- 可共用部分：busy 生命周期、任务检查函数、进度展示、完成/失败后的界面解锁。
- 实施边界：先评估抽取一个很薄的任务生命周期帮助函数是否能消除实际重复；并发度、取消传播、停止时排空活跃请求、写入后对账由具体任务控制。收益不足就不抽。
- 验收：任何异常或取消都能恢复控件；活跃请求结束前不能启动冲突任务；写入结果不明时仍禁止盲目重试。

### 2. 统一目录遍历的共享内核

- 依据：清单导出遍历在 `manifest.js:90`；影视和字幕共用的视频选区遍历在 `media.js:168`、`media.js:186`。媒体预览又有带请求缓存的树读取（`media-panel.js:521`），移动计划需要比较前后目录快照（`media.js:301`）。
- 可共用部分：清单导出和媒体类目录任务之间的 DFS/栈式遍历骨架、循环与重复 ID 防护、取消检查和进度节流。影视与字幕现已共享媒体类选区遍历，不要再分别抽一份。
- 实施边界：抽出可注入的树遍历内核；清单路径/MD5 导出、影视 ancestry 与关联字幕、移动计划快照仍由各自调用者构造。不要把不同结果强行归一成一种“文件树记录”。
- 验收：深目录、重复节点、读取失败、停止后不继续读取等行为有针对性测试；现有文件选择和导出结果保持一致。

### 3. 补齐既有网盘来源接口

- 依据：已有 provider `source` 的共享链路，但 123 导出和导入在 `manifest.js` 各自缓存目录列表；影视选择/预览和移动规划也各自有局部列表缓存。媒体与字幕的写入适配器在 `media.js:301`、`subtitles.js:1122`。
- 可共用部分：只有多处确实需要的只读元数据或目录方法、相同 endpoint 的请求/错误包装。
- 实施边界：先列出方法与调用点，逐对确认参数、授权、节流、错误和确认语义完全一致，再移动小块代码。不要重建已经共享的 `source`，不要把不同写入工作流塞进统一 writer。
- 验收：对应 provider 契约测试覆盖返回形状、分页、权限中断；秒传、移动/重命名、上传对账和回收站的行为保持原样。

## 建议顺序

- 第一阶段先评估任务状态帮助函数，确认实际减少重复后再实现。
- 第二阶段把清单遍历和媒体类遍历的公共骨架做最小原型；若参数和分支多于重复代码，保留现状。
- 第三阶段按调用点清单审查网盘 adapter 的重复，只移动语义完全一致的只读或请求包装。
- 每阶段先检查现有测试覆盖，再补跨功能契约测试；构建和完整回归均通过后才进入下一阶段。

## 明确不列入重构

- `guangya.js` 的新版导入、核验和旧版清理。
- `media.js` 的预览后目录快照复核及移动/重命名。
- `subtitles.js` 的上传回执、同名内容核对、正文验证和结果不明恢复。
- `works.js` 现有的跨功能作品身份与别名共享。

以上前三项看起来都是“写网盘”，实际的风险、对账和失败状态不同。把它们合成一个宽泛的写入框架会削弱保护条件。
